# 商品在庫取込要件

- 文書状態：改訂案
- 更新日：2026年10月1日
- 対象システム：商品在庫管理システム

本書は、商品在庫取込の目的、対象範囲および共通の方針を定める。入力ファイルの要件、保存データの定義、在庫データの利用、取込処理と運用、エラー・警告の条件は、第3章に示す各文書に分割して記述する。

## 1. 目的

SKU別・倉庫区分別の在庫数を取り込み、モールおよび倉庫を横断して一元的に在庫を把握可能とする。取り込んだ在庫は、在庫試算の現在庫として使用し、SKUごとに在庫切れリスクや現在のモール別や倉庫別に在庫数を簡単に確認できるようにする。

在庫は、BOSSおよびAmazonから在庫を取得する別システム（以下「在庫取得システム」）が出力する日次在庫CSVから取り込む。本システムはBOSS・Amazonの在庫レポートを直接取り込まない。

## 2. 対象倉庫と取得元

在庫は倉庫区分単位で管理する。倉庫区分と日次在庫CSVの列の対応は次のとおりである。

| 倉庫区分         | 保管主体   | 出荷対象モール                        | 日次在庫CSVの列    |
| ------------ | ------ | ------------------------------ | ------------ |
| `BOSS自社倉庫`   | 自社     | 楽天市場、Yahoo!ショッピング、au PAY マーケット | `boss_own`   |
| `RFC`        | 楽天     | 楽天市場、Yahoo!ショッピング、au PAY マーケット | `boss_rfc`   |
| `Amazon自社倉庫` | 自社     | Amazon（自社出荷）                   | `amazon_own` |
| `FBA`        | Amazon | Amazon（FBA）                    | `amazon_fba` |

倉庫区分の値は、 [販売実績保存データ 第4.1節](../販売実績取込要件/04.販売実績保存データ.md) の出荷倉庫と同一の語彙とする。販売実績と在庫で別々の倉庫の語彙を持たず、同じ4区分を使用する。倉庫区分の属性は [商品在庫保存データ 第5章](03.商品在庫保存データ.md) の倉庫マスタで一元管理する。

`RFC` は楽天スーパーロジスティクス（RSL）が運営する楽天フルフィルメントセンターを指す。運用上はRSL倉庫とも呼ぶが、BOSS受注実績の出力値が `RFC倉庫` であるため、システム内の倉庫区分は `RFC` に統一する。

`RFC` は楽天市場専用の倉庫ではない。 [販売実績取込要件](../販売実績取込要件/01.販売実績取込要件.md) の実データでは、 `RFC倉庫` からの出荷が楽天市場、Yahoo!ショッピング、au PAY マーケットに発生している。 `RFC` を楽天市場だけの在庫として扱わない。

## 4. 在庫取得システムとの役割分担

| 処理 | 担当 |
| --- | --- |
| BOSS・Amazonからの在庫レポートの取得 | 在庫取得システム |
| AmazonのASIN・出品者SKUからBOSSの`SKUコード`への対応付け | 在庫取得システム |
| 倉庫区分ごとの販売可能在庫の算出 | 在庫取得システム |
| 日次在庫CSVの出力 | 在庫取得システム |
| 日次在庫CSVの取込、検証、倉庫区分別の保存 | 本システム |
| 在庫の手入力、照会、在庫試算への利用 | 本システム |

本システムは、日次在庫CSVの値を取込元の確定値として受け入れ、BOSS・Amazonの元データと照合しない。在庫取得システムの対応付けや算出の誤りは、在庫取得システム側で訂正したCSVを再取込して反映する（[取込処理・運用要件 第2章](05.取込処理・運用要件.md)）。

## 5. 共通方針

### 5.1 在庫の管理単位

在庫はSKU単位ではなく、SKUと倉庫区分の組合せ単位で管理する。1レコードは、1つの在庫基準日における1SKUの1倉庫区分の在庫を表す。

日次在庫CSVは1行に4倉庫区分の在庫数を列として並べる形式であるが、保存時は倉庫区分ごとの行へ分割する。保存形式の選択理由は [商品在庫保存データ 第1.1節](03.商品在庫保存データ.md) に定める。

### 5.2 倉庫を合算しない

BOSSの自社倉庫在庫とAmazonの自社倉庫在庫は、同じ自社保管であっても合算せず、別の倉庫区分として保持する。理由は次のとおりである。

- 合算すると、BOSS側に在庫が潤沢でAmazon側が品薄という状態を検知できなくなる。倉庫別に欠品を判定することが、本機能の主要な目的である（[在庫利用要件](04.在庫利用要件.md)）。
- 社内でもAmazonとBOSSの在庫は分けて管理されており、管理実態と保存構造を一致させる。

したがって次のとおり扱う。

- 欠品発生時期の判定および必要在庫数の算出は、倉庫区分単位で行う。
- 全倉庫の合計在庫は保存せず、表示時に集計する。
- 保存済みの倉庫区分別在庫を、SKU単位の1つの値へ丸めない。

販売実績の出荷倉庫は在庫の倉庫区分と同一の値であるため（[販売実績保存データ 第4.1節](../販売実績取込要件/04.販売実績保存データ.md)）、`販売注文明細.出荷倉庫`をそのまま倉庫区分として扱い、倉庫区分別の販売実績を集計できる。変換表を設けない。

### 5.3 在庫基準日

在庫は、ある時点の残高を表すスナップショットであり、期間の累計を表す販売実績とは性質が異なる。取り込んだ在庫数には、その在庫が成立した日である在庫基準日を必ず付与する。

在庫基準日は、日次在庫CSVの`date`列の値とする。担当者は取込時に在庫基準日を指定しない。1つのファイルに複数の在庫基準日の行が含まれうる（[日次在庫CSV取込要件 第4章](02.日次在庫CSV取込要件.md)）。ファイル名に含まれる日付は判定に使用しない。

日次在庫CSVは1行に4倉庫区分の在庫数を持つため、同一の在庫基準日・SKUについて4つの倉庫区分の在庫は同時に揃う。

### 5.4 追加登録と再取込

在庫数は上書きせず、在庫基準日ごとに追加登録して蓄積する。

- 在庫基準日が異なる在庫数は、別レコードとして追加登録する。
- 同一の在庫基準日・倉庫区分・SKUのレコードが登録済みの場合は、一意キーで既存レコードを特定して更新し、二重登録しない。日次在庫CSVは過去日の行を含みうるため、取込済みの在庫基準日を再び含むファイルを取り込むことは通常の運用で発生する。
- 再取込したファイルに含まれないSKUの既存レコードは、削除も0への書き換えもしない。

再取込時の保存結果は[商品在庫保存データ 第6章](03.商品在庫保存データ.md)に定める。

### 5.5 販売可能在庫だけを保存する

在庫として保存する数量は、倉庫区分ごとの販売可能在庫の1項目だけとする。実在庫数および引当済数は保存しない。

販売可能在庫は、当該倉庫から現在出荷に充てられる数量であり、欠品発生時期および必要在庫数の算出に使用する唯一の在庫値である（[在庫利用要件](04.在庫利用要件.md)）。日次在庫CSVの4倉庫区分の列は販売可能在庫を表し、その算出は在庫取得システムが行う。本システムは実在庫数および引当済数を受け取らず、販売可能在庫を算出しない。

## 6. 商品コードの対応

### 6.1 システム内商品コードの基準

システム内商品コードはBOSSの`SKUコード`を基準とする。この方針は [販売実績取込要件 第5.1節](../販売実績取込要件/01.販売実績取込要件.md) と同一であり、在庫取込のために別の基準を設けない。SKUマスタは販売実績と在庫で共通のマスタを使用する。

日次在庫CSVの`sku`列はBOSSの`SKUコード`であり、変換せずにシステム内商品コードとして採用する。AmazonのASINおよび出品者SKUとの対応付けは在庫取得システムが済ませているため（第4章）、在庫取込ではSKUマスタの子ASINを参照しない。

- `sku`は英字の大小を区別して保存・照合する。
- 前後の空白だけを除去し、内部の空白は除去しない。

### 6.2 未登録SKUの扱い

`sku`がSKUマスタに存在しない場合は、取込を中断せず、当該`sku`を商品属性未設定のSKU識別レコードとして自動登録する。SKUに登録状況を表す状態は付与せず、属性未設定を理由に警告しない。扱いは[販売実績取込要件 第5.4節](../販売実績取込要件/01.販売実績取込要件.md)と同一とする。

`product_code`、`brand`、`category`および`size`は商品マスタ側で管理する属性であり、自動登録したSKUにも設定しない（[日次在庫CSV取込要件 第9章](02.日次在庫CSV取込要件.md)）。

### 6.3 対象SKUの範囲

日次在庫CSVに含まれるSKUの範囲は在庫取得システムの出力対象により決まり、本システムは指定しない。取込ではCSVに含まれるSKUをすべて取り込み、予測対象外または商品マスタ未登録であることを理由に除外しない。

実データは26品番・272SKUを含み、BOSSの全SKUを網羅していない（[日次在庫CSV取込要件 第12章](02.日次在庫CSV取込要件.md)）。このため、在庫照会で全SKUの在庫を確認できるとは限らない。在庫試算の対象SKUがCSVに含まれない場合は、在庫を`0`とせず、在庫未取得として警告する（[商品在庫保存データ 第7章](03.商品在庫保存データ.md)）。

## 7. 未確定事項

実装開始前に、次を確定する。

1. 取込頻度。日次在庫CSVを取得日ごとに取り込むか、複数日分をまとめて取り込むか（[取込処理・運用要件 第2章](05.取込処理・運用要件.md)）。
2. 日次在庫CSVに含めるSKUの範囲。在庫試算の対象品番に属するSKUを必ず含めることを在庫取得システム側で保証するか。
3. `free_stock`および`ec_stock`の意味と、本システムで取り込む必要があるか（[日次在庫CSV取込要件 第9章](02.日次在庫CSV取込要件.md)）。
4. 初回取込で遡る在庫基準日の範囲。在庫取得システムが過去日の在庫をどこまで出力できるか。

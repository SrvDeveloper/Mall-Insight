# 販売実績取込要件

- 文書状態：確定版
- 更新日：2026年8月31日
- 対象システム：販売実績管理システム
- 実データ検証状況：BOSS確認済み、Amazon全注文レポート（注文日基準）確認済み、Amazon全注文レポート（最終更新日基準）確認済み

本書は、販売実績取込の目的、対象範囲および全取込元に共通する方針を定める。取込元ごとの要件、保存データの定義、取込処理と運用、エラー・警告の条件は、第3章に示す各文書に分割して記述する。

## 1. 目的

Amazon、楽天市場、Yahoo!ショッピング、au PAY マーケットの販売実績を取り込み、モール横断で一元的にデータを管理する。初期導入では運用の簡便さを優先し、APIによる自動連携ではなく、BOSSおよびAmazon Seller Centralから出力したCSV・テキストファイルの取込を基本とする。

## 2. 対象モールと取得元

| モール | 現行管理システム | 取得データ | 初期取込方式 |
|---|---|---|---|
| 楽天市場 | BOSS | BOSS受注実績一覧 | CSV取込 |
| Yahoo!ショッピング | BOSS | BOSS受注実績一覧 | CSV取込 |
| au PAY マーケット | BOSS | BOSS受注実績一覧 | CSV取込 |
| Amazon | Amazon Seller Central | 全注文レポート | テキスト取込 |

## 4. 共通方針

### 4.1 販売日の定義

全モール共通で、注文日を販売日として扱う。  
注文を販売実績に含めるかどうかは、各管理システムの注文ステータスに基づいて決定する。  
BOSSは`注文ステータス`が`完了`の受注実績だけをCSVに出力し、取込時にその値を検証する。
Amazonは取込時に`order-status`から販売計上状態を判定する。  
実際の出荷日は販売日の判定に使用しない。

BOSS受注実績CSVの抽出期間は、初回取込では注文日、日次差分取込では出荷日を基準とする。日次差分取込を出荷日基準とするのはCSVへの抽出漏れを防ぐためであり、販売日は従来どおり`モール注文日時`から求める。出荷日を販売日として保存または集計しない。

### 4.2 管理単位

販売実績は注文明細単位で管理する。  
注文単位の情報と注文明細単位の情報を分けて保持し、注文合計金額を明細行数分だけ重複計上しない構造とする。

販売試算、売上および在庫の可視化に必要な項目だけを保存する。  
取込対象の判定、入力値の検証または金額の変換にだけ使用する項目は、取込処理中に参照しても保存しない。

注文明細には出荷倉庫を保持する。出荷倉庫は`BOSS自社倉庫`、`RFC`、`Amazon自社倉庫`、`FBA`の4区分とし、モールではなく倉庫の単位で販売数量を集計できるようにする（[販売実績保存データ 第4.1節](04.販売実績保存データ.md)）。この4区分は在庫の倉庫区分と同一の語彙であり、[商品在庫取込要件](../商品在庫取込要件/01.商品在庫取込要件.md)と共通の倉庫マスタを使用する。販売実績と在庫で別々の倉庫の語彙を持たない。

### 4.3 再取込

同一ファイルまたは同一期間のデータを複数回取り込めるものとする。

- 未登録データは追加する。
- 登録済みデータは一意キーを使用して更新する。
- 再取込によって販売数量や金額を二重計上しない。
- 取込済みファイルの再指定を許可する。
- Amazonの保存済みデータの取込元ステータスが変化した場合は、販売計上状態を更新し、現在の販売実績へ反映する。
- 同じ内容を再取込した場合は、販売計上状態および集計結果を変化させず、同一の状態変更履歴を重複して作成しない。

再取込時の保存結果は [販売実績保存データ 第8章](04.販売実績保存データ.md) に定める。

### 4.4 キャンセル・返品・返金の扱い

キャンセル、返品および返金への対応は、取込処理では完結させず、担当者による手動対応を基本とする。

取込元データからの検出可否は次のとおりである。

| 事象      | BOSS受注実績                                                   | Amazon全注文レポート                        |
| ------- | ---------------------------------------------------------- | ------------------------------------ |
| 注文キャンセル | 検出不可。 `注文ステータス` が `完了` の受注実績だけを出力するため、キャンセルされた注文はファイルに現れない | 検出可能。`order-status`が`Cancelled`へ変化する |
| 出荷後の返品  | 検出不可。該当項目無し。                                               | 検出不可。該当項目無し。                         |
| 返金      | 検出不可。該当項目無し。                                               | 検出不可。該当項目無し。                         |

このため、次のとおり扱う。

- Amazonの取込後のキャンセルだけは、取込元ステータスの変化として自動的に販売実績から除外する（[販売実績保存データ 第7章](04.販売実績保存データ.md)）。
- BOSSのキャンセル、および全モールの返品・返金は、担当者が販売実績を手動で修正する（[販売実績保存データ 第11章](04.販売実績保存データ.md)）。
- 返品・返金データの取込は初期機能では行わない（[第6章](01.販売実績取込要件.md)）。

手動修正は、販売実績の網羅性および取込元との整合性を保証する機能ではなく、担当者が把握した事象を販売実績へ反映するための補助機能として位置づける。取込データとの自動照合、未反映のキャンセル・返品・返金の検知、および反映漏れの警告は行わない。

したがって、キャンセル・返品・返金が反映されていない販売実績が生じうる。需要予測および在庫試算は、この誤差を許容する前提とする。

## 5. 商品コードの対応

### 5.1 システム内商品コードの基準

BOSSの`SKUコード`は、モールに依存せず全社で共通に使用する商品識別コードである。システム内商品コードはこれを基準とし、BOSSの`SKUコード`をそのままシステム内商品コードとして扱う。取込のための独自採番は行わない。

システム内商品コードが指す粒度は、品番ではなく在庫管理単位のSKUである。[要件定義書 第10.1節](../要件定義書.md)のSKUマスタが保持する`SKU`と同一の値であり、上位階層である品番およびカテゴリーはSKUマスタ側で管理する。

### 5.2 取込元ごとの解決方法

| 取込元                                      | 商品識別子  | システム内商品コードの解決          |
| ---------------------------------------- | -------- | ---------------------- |
| BOSS受注実績（楽天市場、Yahoo!ショッピング、au PAY マーケット） | `SKUコード` | 変換せず、`SKUコード`をそのまま採用する |
| Amazon全注文レポート                            | `asin`    | SKUマスタの子ASINを参照して特定する      |

BOSSの`SKUコード`はモールごとに異なる値ではなく、同一商品には全モールで同一の値を使用する。したがってBOSSを取得元とする明細では、取込元SKUとシステム内商品コードが常に一致する。

Amazonの`sku`はAmazon Seller Centralで出品者が設定し変更できる値であり、同一商品に過去および現在の複数の値が存在しうるため、商品コードの解決には使用しない。Amazonが商品ごとに付与し変更できない`asin`を子ASINとしてSKUマスタと照合する。

### 5.3 Amazon子ASINによる対応

Amazon.co.jpでは、1つの子ASINが1つの商品を表し、1つのBOSS SKUに対応する。SKUマスタでは子ASINをAmazon.co.jp内で一意とし、有効・無効状態にかかわらず同一の子ASINを複数のSKUへ登録しない（[商品管理要件 第5.4節](../商品管理要件/01.商品管理要件.md)）。親ASINは複数のSKUを束ねるため、商品コード解決には使用しない。

Amazon SKUは販売注文明細の取込元SKUとして、`asin`は取込元商品IDとして取込時点の値を保存する。Amazon SKUが変化しても、同一の子ASINであれば同じシステム内商品コードとして扱う。Amazon SKUからシステム内商品コードへの対応表は保持しない。

初期リリース時に手動で整備する商品マスタは、設定された判定期間内の品番別純販売数量が登録基準を満たす品番と、その品番に属するSKUに限定する。全SKUについて品番、カテゴリー、カラーおよび度数を登録することはしない。取込に必要なSKU識別レコードはBOSSの`SKUコード`から作成できるが、`SKUコード`から商品属性を機械的に導出しない。Amazonデータの取込対象とするSKUについては子ASINを整備する。

SKUおよび子ASINはCSVによる一括インポートおよびエクスポートができることとする。ファイルの項目構成および更新方式は詳細設計で定める。子ASINの一意性および形式の検証規則は[商品管理要件 第7章](../商品管理要件/01.商品管理要件.md)に従う。

SKUマスタに子ASINが存在しない商品は未対応ASINとして記録し、子ASINの登録後に再取込できるようにする。

子ASINはAmazon上で変更されない識別子とする。誤登録を訂正する場合の過去実績の扱いおよび変更履歴は[商品管理要件 PM-008および要確認事項9](../商品管理要件/01.商品管理要件.md)に定める。

### 5.4 未登録SKUの扱い

BOSSの`SKUコード`がSKUマスタに存在しない場合は、取込を中断せず、当該`SKUコード`を商品属性未設定のSKU識別レコードとして自動登録する。BOSSが全社共通のSKUを付与する基準であるため、販売実績の保存に必要な識別子として扱う。

自動登録したSKUの品番、カテゴリー、カラー、度数等は未設定のままとし、販売実績は通常どおり保存する。SKUに登録状況を表す状態は付与せず、属性が未設定であることを理由に警告も記録しない。未登録SKUは商品・SKUマスタの未登録SKU一覧から担当者が処理する（[商品管理要件 第8.2節](../商品管理要件/01.商品管理要件.md)）。

Amazonの`asin`がSKUマスタの子ASINに存在しない場合は自動登録の対象とせず、未対応ASINとして記録する。Amazon SKUは変更可能であるため、Amazon SKUから対応先を推測しない。

商品マスタ未登録SKUを需要予測でどう扱うかは、[要件定義書 FR-018](../要件定義書.md)に定める。

## 6. 初期対象外

初期機能では、次の機能を対象外とする。

- BOSSとのAPI連携
- Amazon SP-APIによる自動取得
- 実出荷日の管理
- 配送状況・配達完了日の管理
- FBA出荷商品レポートとの突合
- 返品・返金データの取込および販売実績への自動反映
- BOSSのキャンセルの自動検出
- キャンセル・返品・返金の反映漏れの検知および取込データとの自動照合
- 返品日・返金日を基準とした集計
- Amazon手数料の詳細管理
- Amazon入金・決済レポートとの照合
- 会計上の確定売上との照合

キャンセル、返品および返金は、第4.4節のとおり手動対応を基本とし、初期機能には [販売実績保存データ 第11章](04.販売実績保存データ.md) の手動修正だけを含める。取込データによるキャンセル、返品および返金の自動反映は初期リリースでは実装せず、実装時期および実装方法も初期リリース段階では確定しない。将来の機能拡張時に、対象データ、取込方法、既存販売実績への反映方法などを改めて設計し、実装する。

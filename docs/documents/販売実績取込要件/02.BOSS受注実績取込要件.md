# BOSS受注実績取込要件

- 文書状態：確定版
- 更新日：2026年8月31日
- 対象システム：販売実績管理システム
- 実データ検証状況：BOSS受注実績一覧 確認済み

本書は、BOSS受注実績一覧に固有の取込要件を定める。楽天市場、Yahoo!ショッピングおよびau PAY マーケットの販売実績が対象である。  
全取込元に共通する方針は[01.販売実績取込要件](01.販売実績取込要件.md)に、保存項目の全体像と共通の保存形式は[04.販売実績保存データ](04.販売実績保存データ.md)に定める。  
章構成は[03.Amazon全注文レポート取込要件](03.Amazon全注文レポート取込要件.md)と共通であり、その定義は[販売実績取込要件 第4.5節](01.販売実績取込要件.md)による。

## 1. 入力ファイル

| 項目 | 内容 |
|---|---|
| 取得元 | BOSS受注実績一覧 |
| ファイル形式 | CSV |
| 区切り文字 | カンマ |
| 文字コード | Shift_JIS（CP932） |
| 項目名 | 1行目 |
| データ構造 | 1注文明細につき1行 |
| 抽出期間基準 | 初回取込は注文日、日次差分取込は出荷日。任意期間再取込は用途に応じて選択 |

文字コードを明示して読み込み、UTF-8として誤って処理しないこと。

BOSS受注実績一覧をCSVへ出力するときは、初回取込では対象期間の基準に注文日を指定し、過去の受注実績を一括取得する。日次差分取込では出荷日を指定する。日次差分取込を注文日基準にすると、対象期間内に注文されたもののCSV出力時点で`完了`しておらず、その後の対象期間に出荷された注文がいずれのCSVにも含まれず、取りこぼす可能性があるためである。出荷日基準とすることで、対象期間内に出荷されて`完了`となった受注実績を取得する。

CSVには抽出期間の基準および出荷日が含まれないため、システムはファイル内容だけから出荷日基準で出力されたことを検証できない。出力時に指定した対象期間と基準は、取込時に利用者が入力し、取込履歴へ保存する（[販売実績保存データ 第5章](04.販売実績保存データ.md)）。

## 2. 必須列・値の扱い

BOSS受注実績には、最低限次の列が必要である。  
ここでの必須とは列の存在を意味し、各行の値が空欄であることを一律に取込エラーとするものではない。

| 列名 | 用途 | 値の必須 |
|---|---|---|
| `注文ID` | 注文の一意キー | 必須 |
| `ショップID` | モール区分の識別 | 必須 |
| `モール注文番号` | 元モールとの照合 | 必須 |
| `モール注文日時` | 販売日時 | 必須 |
| `注文ステータス` | 取込対象の検証 | 必須 |
| `商品合計金額` | 注文単位の商品金額合計 | 必須 |
| `消費税合計` | 注文単位の税額合計 | 必須 |
| `商品ID` | 注文明細の一意キーおよび取込元商品ID | 必須 |
| `SKUコード` | 取込元SKU | 必須 |
| `商品名` | 商品名 | 必須 |
| `注文個数` | 販売数量 | 必須 |
| `商品単価` | 明細の商品金額 | 必須 |
| `消費税` | 明細の税額 | 必須 |
| `税込別` | `商品単価`の税区分の判定 | 未確定 |
| `倉庫` | 出荷倉庫の判定 | 必須 |

すべての列名は前後の空白を除去してから必須列と照合する。

`注文ステータス`が`完了`の明細では、上表で値を必須とした列に値が存在することを要する。  
`税込別`の許可値、空欄および未知値の扱いは未確定である。  
値の必須条件を満たさない行の扱いは[取込エラー・警告 第2章](06.取込エラー・警告.md)に定める。

## 3. 取込対象

BOSS受注実績から `注文ステータス` が `完了` の受注実績だけをCSVに出力し、取込対象とする。  
取込時には、CSVに含まれる各明細の`注文ステータス`が`完了`であることを検証する。  
`注文ステータス`の値自体は入力ファイルの検証にだけ使用し、そのままの値では保存しない。  
取込元注文ステータスおよび取込元明細ステータスには、`完了`に対応する取込元共通の定数`Shipped`を保存する（[販売実績保存データ 第2章](04.販売実績保存データ.md)）。

`完了`以外の明細は入力検証不合格として登録せず、行単位の取込エラーとする。  
このため、BOSSでは取込元ステータスの変化による保存済みデータの無効化・再有効化は発生しない（[販売実績保存データ 第7章](04.販売実績保存データ.md)）。

BOSSは`完了`の受注実績だけを出力するため、取込後にキャンセルされた注文をファイルから検出できない。  
BOSSのキャンセルは、取込側では対応できないため手動で販売実績へ反映する（[販売実績取込要件 第4.4節](01.販売実績取込要件.md)、[販売実績保存データ 第11章](04.販売実績保存データ.md)）。

## 4. 販売日

`モール注文日時` を販売日時として使用する。  
CSV内の日時にはタイムゾーン情報が含まれていないため、日本時間として扱う。  
日単位で集計する場合は、 `モール注文日時` の日本時間の日付部分を販売日とする。

## 5. モール区分

BOSS受注実績の `ショップID` を使用して、モールを識別する。

| `ショップID` | モール |
|---|---|
| `67419` | 楽天市場 |
| `67572` | Yahoo!ショッピング |
| `67574` | au PAY マーケット |

`ショップID` は5桁の半角数字で構成される文字列として扱う。  
上表に存在しない `ショップID` の明細は、モールを識別できないため取込エラーとする。  
識別したモールは、システム内の所定のモールコードへ変換して保存する。

## 6. 出荷倉庫

BOSS受注実績の`倉庫`を、販売注文明細の出荷倉庫へ変換して保持する。  
`倉庫`は楽天市場を含むBOSS経由の全モールで、次のとおり共通の出荷倉庫へ変換する。

| `倉庫`の値 | 保存する出荷倉庫 |
|---|---|
| `RFC倉庫` | `RFC` |
| `自社倉庫` | `BOSS自社倉庫` |

上表に存在しない値は出荷倉庫を判定できないため、行単位の取込エラーとする。

BOSSの`自社倉庫`は`自社倉庫`のまま保存せず、`BOSS自社倉庫`へ変換する。Amazonの自社出荷分と同一の値になることを避けるためである（[販売実績保存データ 第4.1節](04.販売実績保存データ.md)）。

`RFC倉庫`は楽天市場専用ではない。実データでは、`RFC倉庫`からの出荷が楽天市場86件、Yahoo!ショッピング63件、au PAY マーケット4件に発生している。`ショップID`から出荷倉庫を推定せず、`倉庫`の値だけで判定する。

## 7. 注文・明細の一意キー

注文キーには `注文ID` を使用する。  
注文明細キーには、次の組み合わせを使用する。

```text
注文ID + 商品ID
```

実データでは、次の組み合わせも一意であることを確認している。

```text
注文ID + SKUコード
```

同一注文内に同一 `商品ID` かつ同一 `倉庫` が複数行存在することは通常想定しない。  
複数行存在した場合は、ファイル内で最初に出現した1行だけを取込対象とし、  
2行目以降は重複明細として取込対象外にし、自動的な合算は行わない。

重複明細は取込エラーではなく警告として出力する。  
警告には、注文ID、商品ID、SKUコード、対象外とした行番号および重複件数を記録する。

重複明細を警告として扱う点はAmazonと異なる。Amazonでは2行目以降を行単位の取込エラーとする（[Amazon全注文レポート取込要件 第7章](03.Amazon全注文レポート取込要件.md)）。  
BOSSの一意キーおよび重複処理の妥当性は再検討を要する。

## 8. 注文単位で保持する項目

次の項目は注文単位の情報として保持する。

- 取込元注文ID：`注文ID`
- モールコード：`ショップID` を変換した値
- モール注文番号：`モール注文番号`
- 販売日時：`モール注文日時`を日本時間として扱った値
- 商品金額合計：`商品合計金額`
- 税額合計：`消費税合計`
- 取込元注文ステータス：定数`Shipped`（[販売実績保存データ 第2章](04.販売実績保存データ.md)）

注文単位の合計項目は、複数の明細行に同じ値が繰り返される。そのため、同一`注文ID`につき1回だけ登録・集計する。  
Amazonと異なり、注文単位の合計金額が入力ファイルに存在するため、明細合計との整合性を検証できる（第10章）。

## 9. 注文明細単位で保持する項目

次の項目は注文明細単位の情報として保持する。

- 取込元明細ID：`商品ID`
- 取込元商品ID：`商品ID`
- 取込元SKU：`SKUコード`
- 商品名：`商品名`
- 販売数量：`注文個数`
- 商品単価：税込換算後の`商品単価`
- 商品金額：税込換算後の商品単価 × `注文個数`
- 税額：1点当たりの`消費税` × `注文個数`
- 出荷倉庫：`倉庫`を変換した値（第6章）
- 取込元注文ステータス：定数`Shipped`（[販売実績保存データ 第2章](04.販売実績保存データ.md)）
- 取込元明細ステータス：定数`Shipped`（[販売実績保存データ 第2章](04.販売実績保存データ.md)）

BOSSの`商品単価`および`消費税`は商品1点当たりの金額である。明細単位の金額は`注文個数`を乗じて算出する。  
明細合計金額を直接保持するAmazonとは、金額列の単位が異なる（[Amazon全注文レポート取込要件 第9章](03.Amazon全注文レポート取込要件.md)）。

## 10. 金額の扱い

注文合計金額と明細金額を分けて管理する。

- 注文の商品合計金額：`商品合計金額`
- 注文明細の商品単価：`商品単価`を税込金額へ換算した値
- 消費税：注文単位では`消費税合計`、明細単位では商品1点当たりの`消費税`

`税込別`は、`商品単価`が税込金額か税別金額かを示す。

| `税込別`の値 | `商品単価`の扱い |
|---|---|
| `1` | 税込金額 |
| `1`以外 | 税別金額 |

通常は`1`が出力される。`1`以外の値が設定されている場合は、値の種類にかかわらず税別金額として扱う。  
`税込別`は金額変換にだけ使用し、保存しない。

保存する商品単価は、次のとおり税込金額へ必ず換算する。

```text
税込別 = 1の場合：商品単価
税込別 ≠ 1の場合：商品単価 + 消費税
```

商品合計金額との比較に使用する税込換算後の明細金額は、次のとおり算出する。

```text
税込別 = 1の場合：商品単価 × 注文個数
税込別 ≠ 1の場合：（商品単価 + 消費税）× 注文個数
```

第7章の重複判定を適用した後の取込対象明細について、次の整合性を確認する。

```text
商品合計金額 = 注文明細ごとの税込換算後の明細金額の合計
```

`商品合計金額` と注文明細ごとの税込換算後の明細金額の合計が一致しない場合は、  
該当注文の販売注文および販売注文明細を登録・更新しない。

取り扱う金額はすべて日本円とし、通貨コードは保存しない。

## 11. 0円商品の扱い

商品単価が0円の明細を許可する。  
プレゼント品、同梱品などの可能性があるため、商品単価0円だけを理由に取込エラーとしない。  
0円商品を含む場合は、確認用の警告を記録する（[取込エラー・警告 第3章](06.取込エラー・警告.md)）。

## 12. 個人情報の扱い

販売実績管理に不要な個人情報は取り込まない。  
原則として、次の項目は取込・保存対象外とする。

- 注文者氏名
- 注文者郵便番号
- 注文者住所
- 注文者電話番号
- 送付先氏名
- 送付先郵便番号
- 送付先住所
- 送付先電話番号
- 注文備考
- 配送備考
- 倉庫備考
- ギフト備考

上記の列、および追加列や別形式のファイルに含まれる個人情報は保存対象外とする。

# バックログ

- 文書状態：運用中
- 更新日：2026年10月7日
- 対象システム：ECモール統合分析システム「Mall Insight」

## 1. 書き方

- 上にあるものほど優先度が高い。順番は区切り（1～2週間）ごとに見直す。
- 近いうちに作るものだけ受入条件を書く。先の項目は1行で書き、着手する前に詳しくする。
- 状態は「未着手」「進行中」「完了」とする。完了した項目も削除しない。
- 「旧設計書」は参考資料へのリンクである。そのまま実装するのではなく、作りながら必要な部分だけ採用し、変えた点は[決定記録](03.決定記録.md)に残す。

## 2. リリース1（MVP）

目標：日次在庫と販売実績を取り込み、売上上位の品番について、12か月在庫推移を本物の数字で確認できる。

予測は単純な平均日販だけで出し、季節性やバックテストは使わない。まず流れを最後まで通すことを優先する。

### B-001 画面とAPIをつなぐ土台

- 状態：完了（2026年10月6日）
- 内容：Vueの画面からLaravelのAPIを呼び、DBのデータを表示できる状態にする。あわせて、全画面で使う枠（ヘッダー・メニュー）を作る。
- 受入条件
  - ヘッダーとメニューがあり、メニューから各画面へ移動できる。メニューには作り終えた画面だけを載せる。画面の見た目は新しく考える（K-010）。
  - 品番・SKUのテーブルを、CrossWalkerの実データに合わせた項目で作る（K-012）。品番に属していないSKUも保存できる形にする。在庫・販売実績・入荷予定のテーブルは、それぞれB-003・B-004・B-007で作る。
  - API（`/api/...`）の正常時・エラー時のレスポンスの形が統一されている。
  - 画面からAPIを呼ぶ共通の仕組みがあり、通信エラーやサーバーエラーのときは画面にメッセージを表示する。
  - 品番・SKUの一覧画面があり、サンプルデータがDB→API→画面の順に表示される。この画面はB-002で取得した品番・SKUの確認に使う。
  - テスト用のサンプルデータを投入できる。
  - ルートの `CLAUDE.md` の古い記述（Laravel Boost未導入、`app.ts` が無い等）を現状に合わせる。
  - ログインとAPIの利用制限はB-009で行う。

### B-002 商品（品番・SKU）をCrossWalkerのAPIから取得する

- 状態：完了（2026年10月6日）
- 内容：CrossWalkerのAPI（`GET /items`、`status=all`）から、品番と所属SKUを全件取得して保存する（K-008）。
- 受入条件
  - 品番（品番コード、ブランド、カテゴリー、親ASIN、状態、更新日時）とSKU（SKUコード、子ASIN、状態、TQ品番、TQカラーNo、TQサイズ）を保存する。
  - 取得し直すと、保存済みの品番・SKUが最新の内容に更新される。無効（`inactive`）の品番・SKUも状態付きで保存する。
  - SKUと品番の対応はAPIの親子関係だけで決め、SKUコードから品番を推測しない（例：品番 `si-01sap` のSKUは `si-01sa-1-15`）。
  - APIに接続できない、または認証・回数制限のエラーのときは、前回取得した日時を表示して警告する。
  - 品番・SKUの画面（B-001で作成）で、取得した品番・SKUを確認できる。画面上部に、最後にCrossWalkerから取得した日時と結果を常に表示する（K-017）。
  - 毎朝6時に自動で取得し、画面のボタンからも取得できる（K-018）。
- API仕様と実データの差異（2026年10月6日の接続テストで確認）
  - 品番に、仕様書に無い `name` 項目がある。全55品番で `null`。過去の名残とみられるため保存しない（K-011）。
  - サイズなしのSKUは、仕様書では `tq_size` が空文字だが、実データは `"0"`（サングラス等の22 SKU）。空文字のSKUは無い。
  - 入力エラー時の `errors` の文言が、`validation.between.numeric` のような翻訳キーのまま返る。画面には `errors` の文言をそのまま表示しない。
- 接続テスト時点の件数：55品番、581 SKU（うち無効4、子ASIN未設定10）。`per_page=100` の1回で全件を取得できる。

### B-003 日次在庫をZeroStockViewのAPIから取得する（PG-120）

- 状態：完了（2026年10月6日）
- 内容：ゼロ在庫照会システム「ZeroStockView」のAPI（`GET /inventory/daily`）から、SKU別・在庫の区分別の日次在庫を取得する（K-007・K-020・K-021）。
- 受入条件
  - 在庫は在庫基準日×SKU×在庫の区分（6区分）で保存する。取得できた在庫基準日はその日の在庫をまるごと置き換え、取得できなかった日（調査のない日）は変更しない。
  - 初回は履歴を取れるだけ取り込み、2回目以降は直近7日分を取り直す。前回の最新日より前から途切れている場合は、そこから取り直す。
  - 毎朝10時に自動で取得し、「在庫の取得」画面のボタンからも取得できる。画面には最後に取得した日時と結果、取得済みの在庫基準日の一覧を表示する。
  - CrossWalkerに無いSKUも、品番に未登録のSKUとして保存する。
  - 最新の在庫基準日と経過日数を表示し、4日以上たっていたら在庫が古いと警告する。
  - APIに接続できないときは、前回取得した日時と理由を表示する。在庫を0として扱わない。
- API仕様と実データの差異（2026年10月6日の接続テストで確認）
  - 1回に指定できる期間は、仕様書では365日だが、実際は31日を超えると 422（「対象期間は31日以内で指定してください。」）になる。31日ずつ区切って取得する。
  - 存在しない品番を `product_code` に指定すると、`errors` の文言が `validation.exists` のような翻訳キーのまま返る（本システムは `product_code` を使わない）。
  - 調査のない日（土日など）は返らない（仕様書どおり）。履歴は2026年9月16日から。
  - 対象は28品番・292 SKUで、CrossWalkerの品番の一部。全SKUがCrossWalkerに存在し、品番も一致する。`size` はCrossWalkerの `tq_size` と一致する。
  - カテゴリー名が2品番でCrossWalkerと異なる（`fl-3000`・`flh-001ph` が「調光老眼鏡」、CrossWalkerは「老眼鏡」）。商品情報はCrossWalkerを正とし、ZeroStockViewのブランド・カテゴリーは使わない（K-019）。
- API仕様：[ZeroStockView API仕様](../参考/API仕様/ZeroStockView/API仕様.md)

### B-004 販売実績を取り込む：BOSS受注実績（PG-110）

- 状態：完了（2026年10月6日）
- 内容：BOSSの受注実績一覧から出力したCSV（Shift_JIS）を「販売実績の取込」画面から取り込む（K-022）。Amazonは後回しにする（B-101）。
- 受入条件
  - ファイルを選んで取り込むと、データ行数・新しく登録・上書き・重複で対象外・エラーで未登録・CrossWalkerに無いSKUの件数と、エラー・警告の一覧（行番号・注文ID・SKUコード・内容）が表示される。
  - 同じファイルを2回取り込んでも、実績が二重にならない（注文IDで識別し、取り込み直した注文は明細をまるごと置き換える）。
  - 保存するのは販売日・モール・SKU・出荷倉庫・数量・金額（税込）だけとする（K-024）。
  - 品番に未登録のSKUの実績も取り込み、そのSKUを未登録SKUとして保存する。
  - 文字コード違い・必要な列が無いファイルは、理由を示してファイル全体を取り込まない。
  - 注文ステータスが「完了」でない行、必須の値が空欄の行、ショップID・倉庫を判定できない行は、理由を示してその行だけ取り込まない。
  - 商品合計金額と明細の合計が一致しない注文は登録しない。同じ注文に同じ商品IDの行が複数あれば最初の行だけを取り込み、警告にする。商品単価0円の明細は警告にする。
  - 個人情報（注文者・送付先の氏名・住所・電話番号、備考）は保存しない。
  - 取込の履歴を確認でき、過去の取込の結果とエラー・警告を開ける。
- サンプル（`docs/参考/販売実績取込データ/BOSS受注実績.csv`）での確認結果（2026年10月6日）
  - 526行中524行を登録（475注文。楽天市場300・Yahoo!ショッピング158・au PAY マーケット17）。取り込み直しても二重にならないことを確認した。
  - 273種類のSKUのうち127種類がCrossWalkerに無く、未登録SKUとして保存された（B-010で一覧する）。
  - 注文 `223755315`（338・339行目）は、2つのSKUがそれぞれ8,250円なのに商品合計金額が8,250円で、金額が一致しないため登録されなかった。この扱いのままとする（K-023）。
  - 1つの注文が2つの倉庫から出荷されている注文が7件あった。出荷倉庫は明細ごとに持つため問題ない。
- 旧設計書：[BOSS受注実績取込要件](../documents/販売実績取込要件/02.BOSS受注実績取込要件.md)

### B-010 CrossWalkerに未登録のSKUを一覧する

- 状態：完了（2026年10月7日）
- 内容：販売実績や在庫には出てくるのに、どの品番にも属していないSKUを、品番・SKUの画面で一覧できるようにする（K-017）。B-004の後に作る。
- 受入条件
  - 品番に属していないSKUを、直近12か月の販売数量が多い順に一覧できる（K-029）。
  - 未登録SKUの件数を画面上部に表示する。0件のときは「未登録のSKUはありません」と表示する。
  - 各SKUについて、販売実績・在庫のどちらに出てきたか、最初と最後に出てきた日を確認できる。
  - 担当者はこの一覧を見て、CrossWalkerにSKUを手で登録する（K-025）。登録すると、次のCrossWalkerからの取得で品番に属し、一覧から消える。
  - CrossWalkerへ「登録待ち」として自動で登録する仕組みは、CrossWalker側の改修後に作る（B-120）。
- 確認結果（2026年10月7日）：品番・SKUの画面の「未登録SKU」タブに、BOSS受注実績のサンプルで見つかった127件が販売数の多い順に表示されることを確認した。

### B-005 対象品番を選ぶ（PG-710）

- 状態：完了（2026年10月7日）
- 内容：直近12か月の売上金額が多い順に品番を並べ、在庫試算の対象にする品番を確定する。毎年度初め（4月）に見直すことを基本とし、いつでも変更できる（K-030）。
- 受入条件
  - 品番ごとの売上金額と順位が表示される（K-032）。対象品番が未確定のときは、上位20品番（同順位を含む）が候補として選ばれた状態になっている（K-031）。
  - 候補を入れ替えて、100品番以内で確定できる（K-031）。
  - 確定すると新しい選定として記録され、前の選定は残る。最新の選定が、需要予測と在庫推移の対象になる（K-030）。
  - 今の対象品番をいつ確定したかを表示する。今年度（4月1日以降）に確定していなければ、見直しを促す。
  - 今の対象品番の欄の「確定履歴」ボタンから、確定の履歴をモーダルで新しい順に確認できる。各回の確定日時・確定した人・品番数・前回からの変更（追加・外した品番）・メモと、確定時の順位・売上金額を見られる（K-033）。
- 旧設計書：[要件定義書 FR-042](../documents/要件定義書.md)

### B-006 需要予測を出す（平均日販による単純な予測）

- 状態：進行中
- 内容：対象品番のSKUについて、平均日販から12か月分の月別需要予測を出す（K-035・K-036）。
- 受入条件
  - 直近30日・31〜90日前・91〜180日前の平均日販を0.5・0.3・0.2の重みでまとめた基準平均日販から、今月から12か月分の月別の需要予測を出す。期間は取り込んだ販売実績の最新日から重ならずに遡って数える（K-036）。
  - 欠品していた日（AmazonとBOSSの在庫の合計が0以下の日）は、販売数と日数の両方から除く（K-037）。
  - 販売実績の日数が足りないSKU、欠品していた日が多いSKU、直近180日に1点も売れていないSKUは、0ではなく「予測不能」と理由を表示する。
  - 計算日時・販売実績の期間と、SKUごとに使った期間・販売数・販売日数・欠品日数・平均日販・重みを確認できる。
  - 予測は保存せず、画面を開くたびに最新の販売実績で計算する。
- 旧設計書：[平均日販](../documents/システム需要予測設計/03.平均日販.md)

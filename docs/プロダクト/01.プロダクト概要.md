# プロダクト概要

- 文書状態：運用中
- 更新日：2026年10月6日
- 対象システム：ECモール統合分析システム「Mall Insight」

## 1. 目的

SKUごとに「いつ在庫が足りなくなるか」「いくつ発注すべきか」を、担当者の思い込みではなく販売実績にもとづく需要予測から判断できるようにする。  
現行のExcelでは、昨年実績をもとに担当者が手入力で補正した値を使っており、需要の見込みと販売目標が混ざっている。このため、欠品や過剰在庫の判断の根拠があいまいになっている。

## 2. 変えない原則

機能を足したり作り直したりしても、次の5つは守る。

| No | 原則 | 理由 |
| --- | --- | --- |
| 1 | 「販売実績」「年間販売目標」「システム需要予測」を別のデータとして持ち、在庫試算にはシステム需要予測だけを使う | 目標（願望）で発注すると過剰在庫になる |
| 2 | データが無い、古い、計算できないときは0にせず、「算出対象外」などと表示して警告する | 0と表示すると「在庫が無い」「売れない」と誤解される |
| 3 | 取り込んだ元データは上書きしない。修正や補正は別の値として持つ | 後から何を変えたか確認できなくなる |
| 4 | 計算した数字には、使ったデータ・計算式・計算日時を確認できる導線を付ける | 数字を信用して発注判断に使えるようにする |
| 5 | 在庫試算の結果は保存せず、画面を開くたびに最新データで計算する | 古い試算結果で判断することを防ぐ |

## 3. 利用者

| 利用者 | 主な使い方 |
| --- | --- |
| 在庫担当者 | 実績・在庫の取込、対象品番の確定、入荷予定の登録、在庫推移の確認 |

## 5. 進め方

設計書を先に作り込むやり方をやめ、小さく作って確かめながら進める。

1. 作りたい機能は[バックログ](02.バックログ.md)に優先順に並べる。
2. 1～2週間を1区切りとし、区切りごとに画面・API・DBまで通して実際のデータで動く機能を作る。画面だけ先に作ることはしない。
3. 動かして確かめた結果を見て、バックログの順番と中身を見直す。
4. 作りながら決めたことは[決定記録](03.決定記録.md)に1行ずつ残す。

### 5.1 完成の条件

バックログの1項目は、次をすべて満たしたら完成とする。

- バックログに書いた受入条件を満たし、実際のデータ（またはサンプルデータ）で動く。
- 計算や取込の処理にテストがある。
- `npm run check` と `php artisan test` が通る。
- 決めたことを決定記録に残した。

### 5.2 文書の扱い

- 詳しい仕様書は新しく作らない。必要な仕様はバックログの受入条件と決定記録に書く。
- `docs/documents/` の旧設計書は参考資料として残し、更新しない（[docs/documents/README.md](../documents/README.md)）。計算式や取込形式を調べるときは参照してよいが、決定記録と食い違う場合は決定記録を優先する。
